## 1.3. Домовленості команди (working agreement)

- Канал зв'язку: Telegram, груповий чат команди; час відповіді — до 4 год у будні (9:00–21:00).
- Асинхронний standup: щодня, будні дні, до 20:00 — два рядки «зроблено / що блокує».
- Строки внутрішньої здачі: чернетки — за 3 дні до Demo; рецензування — за 2 дні; зведення інкременту — за 1 день.
- Правила комітів і гілок (з С4): `feature/<номер-задачі>-<коротка-назва>`, повідомлення з ID артефакту (`[TC-07] …`), merge через PR після рецензії.
- Спільні документи: репозиторій GitHub `oleksandragorbonos-maker/tzap`; назви файлів — латиницею без пробілів, з продуктом/спринтом/датою/авторами всередині документа.
- Вирішення суперечок: якщо команда не дійшла згоди за 15 хв обговорення в чаті — тай-брейкер робить Скрам-майстер поточного спринту.

## 1.4. Методологія роботи команди

| Рівень | Що застосовує команда |
|---|---|
| Методологія | Полегшений Scrum: 5 двотижневих спринтів, кожен — Sprint Planning → асинхронні standup → Demo (10 хв) → бліц → Retro (Start/Stop/Continue) → анонімний peer-review; ролі ротуються щоспринта. |
| Методи | User stories за шаблоном «Як…, я хочу…, щоб…» з простежуваністю до очікувань замовника; BPMN 2.0 моделювання бізнес-процесів; рецензування артефактів за чек-листами (не власна робота); трасування вимога → тест-кейс → дефект (з С2). |
| Прийоми | Асинхронний standup замість щоденних зустрічей; ретроспектива Start/Stop/Continue; правило «один виконавець — один рецензент» для кожного артефакту; ведення таблиці задач/Jira з ID артефакту в кожному коміті. Приклад точної послідовності кроків — експорт BPMN-моделі: (1) відкрити `.drawio` у app.diagrams.net; (2) перевірити, що модель пройшла рецензування за чек-листом (`bpmn/review.md`); (3) File → Export as → PNG; (4) зберегти під тим самим іменем, що й вихідник, у ту саму папку `docs/sprint1/bpmn/`; (5) закомітити файл і оновити статус у `tasks.md`. |
